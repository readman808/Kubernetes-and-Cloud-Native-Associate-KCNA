SolrCloud in 5 minutes

Solr is a search server built on the Lucene library. In SolrCloud mode, several Solr nodes cooperate as one cluster. Almost every incident below comes down to which of these building blocks is unhealthy.

Collection

A logical index, such as products. Clients talk to the collection, never to individual servers.

Shard

A slice of the collection's documents. More shards means more data and more write throughput.

Replica and core

A copy of a shard. Each replica lives on one node as a core, a Lucene index directory on disk. More replicas means more query capacity and redundancy.

Leader

One replica per shard is elected leader. Every update to the shard goes through it. No leader means no writes to that shard.

ZooKeeper

Stores the cluster state and runs elections. Without a ZooKeeper connection a Solr node cannot serve as part of the cluster.

Commits and searchers

New documents become searchable only after a commit opens a new searcher, which warms its caches. A hard commit makes data durable. A soft commit only makes it visible.

The rule that explains most incidents: a pod being Running says nothing about whether its cores are healthy, whether it reached ZooKeeper, or whether a shard has a leader. Check each layer separately.

Solr on Kubernetes

The simulator uses the layout a Helm chart or the Solr Operator produces. Know which Kubernetes object holds each piece of state, because the fix usually lives there.

ThingKubernetes objectWhy it matters
Solr nodesStatefulSet solr (pods solr-0..2)Stable names and stable storage. Change settings with kubectl set or patch on the StatefulSet, and the pods roll.
Index filesPVC data-solr-N mounted at /var/solrThe index lives on this volume, so it survives pod restarts and fills up independently per pod.

Restarting a pod is rarely the fix. A restarted pod reads the same environment, mounts the same disk and rejoins the same cluster state. It only helps if the problem lived in memory.

The method

Work from the outside in. At each layer, run one command that proves the layer is healthy before moving to the next. Stop at the first layer that fails.

  1. Pod

    Is it Running and Ready? Restarts? What was the last exit reason?

    kubectl get pods
kubectl describe pod solr-0

  2. Process logs

    Find the first ERROR or SEVERE after startup. Later errors are usually consequences.

    kubectl logs solr-0
kubectl logs solr-0 --previous

  3. Dependencies

    Can the pod resolve and reach ZooKeeper? Is the disk writable and not full?

    kubectl exec solr-0 -- nslookup zk-0.zk-headless
kubectl exec solr-0 -- df -h

  4. Cluster state

    Ask SolrCloud what it believes: live nodes, shards, replica states, leaders.

    curl "http://localhost:8983/solr/admin/collections?action=CLUSTERSTATUS&collection=products"

  5. Core and query behavior

    Which cores failed to load? How often does Solr commit? What do the metrics say?

    curl "http://localhost:8983/solr/admin/cores?action=STATUS"
curl "http://localhost:8983/solr/admin/metrics?group=core&prefix=UPDATE"

Do

  • Read before you write. Every investigation command here is read-only.
  • Change one thing, then verify.
  • Prefer the smallest, most reversible fix.
  • Note the time and the commands, for the post-incident review.

Do not

  • Delete anything under /var/solr/data to free space.
  • Delete a replica before you know another healthy copy exists.
  • Restart everything "to see if it helps".
  • Use a destructive Collections API call (DELETE, DELETESHARD) while diagnosing.

SEV-2Incident 1Layer: pod resources

Pod keeps restarting

Concept: heap is not the whole process

The JVM heap (-Xmx) holds Java objects. The process also needs memory for metaspace, thread stacks, direct buffers and the GC itself, so total usage is above the heap. Kubernetes enforces the container limit with the kernel OOM killer: when the process crosses it, the kernel sends SIGKILL and the container exits with code 137. Rule of thumb: limit ≥ heap × 1.3. Keep extra RAM free for the OS page cache, since Lucene reads index files through it.

Symptoms

  • CrashLoopBackOff with a growing restart count.
  • Logs end abruptly, with no stack trace, often just Killed.

Diagnose

  1. Confirm the pod state.

    kubectl get pods

  2. Read Last State. Reason: OOMKilled and Exit Code: 137 confirm it. Note Limits and the SOLR_JAVA_MEM value.

    kubectl describe pod solr-0

  3. Compare the two numbers. A 1Gi limit with a 2g heap can never work.

    kubectl top pods

Fix (pick one)

# A. give the container headroom above the heap
kubectl set resources statefulset/solr --limits=memory=3Gi

# B. or make the heap smaller than the limit
kubectl set env statefulset/solr SOLR_JAVA_MEM="-Xms512m -Xmx512m"

Verify

  • kubectl get pods shows 1/1 Running with the restart count no longer rising.
  • kubectl top pods stays well under the limit.

Common mistakes

  • Setting the limit equal to the heap (2Gi limit, 2g heap) still gets killed.
  • Deleting the pod. It comes back with the same limit.

Prevent

  • Set requests equal to limits for Solr.
  • Alert on working-set memory nearing the limit.
SEV-2Incident 2Layer: cluster state

Shard with no leader

Concept: leader election and recovery

Each shard elects a leader through ZooKeeper. A replica that was offline recovers by syncing from the leader. If every replica of a shard restarts uncleanly, each may refuse to lead because another one might have newer data, and none can sync because there is no leader. The shard is deadlocked in recovering. FORCELEADER breaks the tie by promoting a replica and accepting that the very latest writes might be missing.

Symptoms

  • Update errors: No registered leader was found after waiting for 4000ms, collection: products slice: shard2.
  • Queries touching that shard return 503. All pods are Running.

Diagnose

  1. Ask for the cluster state. In the JSON, look at each shard's replicas.

    curl "http://localhost:8983/solr/admin/collections?action=CLUSTERSTATUS&collection=products"

  2. Healthy shards have one replica with "leader": "true". Here shard2 has none and both replicas show "state": "recovering".

  3. Confirm in the logs of the nodes that host the shard.

    kubectl logs solr-1

Fix

curl "http://localhost:8983/solr/admin/collections?action=FORCELEADER&collection=products&shard=shard2"

Verify

  • Run CLUSTERSTATUS again: shard2 has a leader and its replicas are active.
  • A test update and a query against /solr/products/select both succeed.

Common mistakes

  • rollout restart. The replicas come back in the same deadlock.
  • Adding replicas. A new replica also has nobody to sync from.
  • Running FORCELEADER on a healthy shard. It does nothing.

Prevent

  • Roll pods one at a time, waiting for Ready between each.
  • Alert on any shard with no leader.
  • After FORCELEADER, reindex recent documents if your pipeline allows replay.
SEV-1Incident 3Layer: dependency and DNS

Pods Running but never Ready

Concept: Kubernetes DNS for StatefulSets

A StatefulSet behind a headless service gives each pod a stable DNS name: <pod>.<service>, for example zk-0.zk-headless. Solr finds ZooKeeper only through the ZK_HOST string, so each name in it must match a real service and pod. A wrong name fails DNS lookup (NXDOMAIN), Solr cannot open a session, and the readiness probe keeps returning 503. Pod Running means the container started, not that the app is usable.

Symptoms

  • 0/1 Running on every Solr pod, rollout stuck.
  • Admin UI: "Solr is not connected to ZooKeeper".

Diagnose

  1. Read the first error in the logs. Look for UnknownHostException and the host Solr tried.

    kubectl logs solr-0

  2. List the real service names.

    kubectl get svc

  3. Prove which name resolves from inside the Solr pod.

    kubectl exec solr-0 -- nslookup zookeeper-0.zookeeper-headless
kubectl exec solr-0 -- nslookup zk-0.zk-headless

  4. Optionally confirm ZooKeeper itself is healthy, so you do not chase it.

    kubectl exec zk-0 -- zkServer.sh status

Fix

kubectl set env statefulset/solr ZK_HOST=zk-0.zk-headless:2181,zk-1.zk-headless:2181,zk-2.zk-headless:2181

Verify

  • The StatefulSet rolls and kubectl get pods shows 1/1 for all Solr pods.
  • CLUSTERSTATUS lists all three live nodes.

Common mistakes

  • Restarting ZooKeeper. It was healthy all along.
  • Using port 2888 or 3888. Clients use 2181.
  • Listing only one ZooKeeper host. It works but is a single point of failure.

Prevent

  • Generate ZK_HOST from the same value that names the ZooKeeper release.
  • Run helm template and diff before upgrades.
SEV-2Incident 4Layer: storage

Disk full

Concept: why Lucene needs free space

A Lucene index is a set of immutable segment files. Commits write new segments and background merges combine small segments into larger ones, temporarily needing space for both the old and new files. A volume that is nearly full cannot merge or commit, so writes fail with No space left on device. Keep usage below about 80%. Each pod has its own PVC, so one hot shard can fill while its neighbours are fine.

Symptoms

  • java.io.IOException: No space left on device in the logs, updates return HTTP 500.
  • The PVC alert fires for one pod only.

Diagnose

  1. Check usage on the suspect pod, then on a neighbour for comparison.

    kubectl exec solr-0 -- df -h
kubectl exec solr-1 -- df -h

  2. See what is using the space.

    kubectl exec solr-0 -- du -sh /var/solr/*

  3. Decide what is safe. data is the live index and is off limits. backups and old logs are not live data.

    kubectl exec solr-0 -- ls -lh /var/solr/backups

  4. Check whether the volume can grow instead.

    kubectl get pvc
kubectl get storageclass

Fix (pick one)

# A. remove stale backups (confirm they exist elsewhere first)
kubectl exec solr-0 -- rm -rf /var/solr/backups/*

# B. grow the volume (needs allowVolumeExpansion: true)
kubectl patch pvc data-solr-0 -p '{"spec":{"resources":{"requests":{"storage":"40Gi"}}}}'

Verify

  • df -h shows usage comfortably below 80%.
  • A test update to the collection succeeds.

Common mistakes

  • Deleting anything inside /var/solr/data. That destroys the shard's index.
  • Clearing only logs. It freed 100 MB of 6 GB needed.
  • Shrinking a PVC. Kubernetes only allows growth.

Prevent

  • Send backups to object storage.
  • Alert at 80%.
  • Verify the StorageClass allows expansion before you need it.
SEV-3Incident 5Layer: commit configuration

Slow queries, CPU pinned

Concept: commits, searchers and warming

A hard commit (autoCommit) flushes data to disk for durability and, with openSearcher=false, does not change what queries see. A soft commit (autoSoftCommit) opens a new searcher so new documents become visible. Every new searcher warms its caches by replaying queries, which costs CPU. If searchers are opened faster than they finish warming, Solr logs Overlapping onDeckSearchers and queries slow down. The cure is to open searchers less often, matching the freshness you actually need.

Symptoms

  • p95 latency jumps; one or more nodes at very high CPU.
  • Logs repeat PERFORMANCE WARNING: Overlapping onDeckSearchers=2 many times a second.

Diagnose

  1. Find the busy node and read its logs.

    kubectl top pods
kubectl logs solr-1

  2. Check the update handler settings. Here autoSoftCommit.maxTime is 100 ms.

    curl localhost:8983/solr/products/config/updateHandler

  3. Confirm with metrics: a huge softAutoCommits count.

    curl "localhost:8983/solr/admin/metrics?group=core&prefix=UPDATE"

Fix

Change the setting with the Config API. It is stored in ZooKeeper, so it survives restarts and applies to every replica.

curl -X POST -H 'Content-type:application/json' -d '{"set-property":{"updateHandler.autoSoftCommit.maxTime":60000}}' http://localhost:8983/solr/products/config

Verify

  • The overlapping-searcher warnings stop and CPU falls.
  • /config/updateHandler shows the new value; /config/overlay lists it as an override.

Common mistakes

  • Raising maxWarmingSearchers. The warning goes away, but more warmups run at once and CPU stays high.
  • Changing autoCommit (the hard commit). It does not open searchers.
  • Restarting pods. The setting comes back from ZooKeeper.

Prevent

  • Choose the soft-commit interval from the real freshness requirement.
  • Do not send commit=true on every indexing batch.
  • Watch the soft-commit rate as a metric.
SEV-3Incident 6Layer: core and index files

Corrupt replica

Concept: replicas are disposable copies

Each replica holds a full copy of its shard, and a new replica can copy the index from the leader. So when a core's files are damaged and another healthy replica exists, the right fix is to replace the damaged replica, not repair it. Tools such as Lucene's CheckIndex -exorcise drop broken segments and the documents in them, leaving this replica inconsistent with its leader. Corruption (CorruptIndexException, bad checksum) usually follows an unclean shutdown or a disk problem.

Symptoms

  • All pods Running, but one replica is down and never recovers.
  • Logs: Unable to create core caused by CorruptIndexException: checksum failed.

Diagnose

  1. Find the failing core in the pod logs.

    kubectl logs solr-0

  2. List failed cores on that node.

    curl "localhost:8983/solr/admin/cores?action=STATUS"

  3. Check that a healthy copy exists. In CLUSTERSTATUS, the same shard must have another replica that is active. Note the failed replica's name (here core_node1).

    curl "localhost:8983/solr/admin/collections?action=CLUSTERSTATUS&collection=products"

Fix

# 1. remove the broken replica
curl "localhost:8983/solr/admin/collections?action=DELETEREPLICA&collection=products&shard=shard1&replica=core_node1"

# 2. create a fresh one; it copies the index from the leader
curl "localhost:8983/solr/admin/collections?action=ADDREPLICA&collection=products&shard=shard1"
If a shard has only two replicas, run ADDREPLICA first and delete the broken one afterward. That way you never run with a single copy.

Verify

  • CLUSTERSTATUS: shard1 has two active replicas and one leader.
  • Document counts match across replicas.

Common mistakes

  • Deleting the healthy replica by mistake. Always match the replica name to the failing core.
  • Using CheckIndex -exorcise. It loses documents.
  • Removing the core directory by hand. ZooKeeper still lists the replica.

Prevent

  • Always run at least two replicas per shard.
  • Give pods a long termination grace period so Solr shuts down cleanly.

Glossary

TermMeaning
AutowarmReplaying recent queries or cache entries into a new searcher so first queries are fast.
Config APIHTTP endpoint that changes a collection's configuration at runtime, stored in ZooKeeper.
CoreOne Lucene index directory on a node, the on-disk form of a replica.
